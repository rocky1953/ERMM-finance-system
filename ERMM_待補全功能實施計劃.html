Part 1：專案總覽

1.1 專案背景與目標

ERMM 財務模組已完成「數據彙整 → 指標計算 → 風險預警」的基礎建設，讓高階主管能即時看到企業體溫。但要真正實現「一眼看出問題 → 立即落實行動 → 持續驗證成效」的閉環，需補強 10 項功能。

專案總目標 將系統從「報表工具」升級為「經營決策中樞」，讓高階主管無需等待月底報表、無需人工找原因，登入即可看到問題、系統自動給原因、一鍵派任務並追蹤成效。

關鍵技術
貢獻度分解算法

功能目標

當任一 KPI 指標（毛利率、負債比、應收周轉等）顯示紅燈或異常波動時，系統自動分析並回傳「前 3 大拖累原因」（哪個公司別、哪個月份、哪個科目貢獻度最高），主管無需手動查帳。

具體實施步驟

  1. 定義異常規則：確認哪些指標需觸發診斷（毛利率↓>5%、負債比↑>10%、應收周轉↓>15%、Z-Score 進入紅區等），建立 anomaly_rule 設定表。
  2. 設計貢獻度分解算法：對異常指標，沿「公司別 → 月份 → 會計科目」三層拆解，計算每個維度對總變動的貢獻百分比（如：毛利率下滑 8%，其中 HM 公司貢獻 -5%、SZ 貢獻 -3%）。
  3. 後端 API 開發：新增 GET /api/kpi-query/diagnosis?bu_no&YYYY_MM&kpi_id，回傳 { anomaly: true, top_reasons: [{dim, value, contribution_pct}], summary }。
  4. 前端整合：在 Dashboard / KPI 頁面的紅燈卡片旁加「🔍 為什麼紅燈？」按鈕，點擊彈窗顯示 Top3 原因與貢獻度橫條圖。
  5. 快取與排程：對熱門查詢結果做 Redis 快取（TTL 1 小時）；每月結帳後用 node-cron 預先計算異常報告。
  6. 驗收測試：準備 3 組測試數據（毛利率下滑、負債比攀升、應收逾期暴增），驗證診斷結果與人工查帳一致。

所需資源

資料庫新增 anomaly_rule 表 + anomaly_log 日誌表
後端新增 1 個路由檔 routes/diagnosis.js，約 300 行
前端新增診斷彈窗元件，整合至 dashboard.js 與 kpiQuery.js
財務顧問確認 6~8 個核心異常規則的門檻值

預期效果

主管看到紅燈後，點擊 1 次即可知道 Top3 原因，不再需要召集會議、請財務部人工查帳。問題定位時間從「數小時」縮短為「數秒」。

工作流狀態機

功能目標

從紅燈指標「一鍵建立行動任務」，支援指派負責人、設定截止日與改善目標，並在儀表板追蹤進度，形成「發現問題 → 派任務 → 執行 → 驗證成效」的閉環。

關鍵技術
node-cron + Email/LINE API

功能目標

當指標觸發預警條件時（Z-Score 進入破產區、負債比超過 70%、應收逾期超過 60 天等），自動發送 Email / LINE / 簡訊給對應主管，並附帶建議處置，讓主管被動變主動。

具體實施步驟

  1. 預警規則配置：建立 alert_rule 表（指標、條件、閾值、通知管道、通知對象、冷卻時間），支援 UI 配置。
  2. 定時掃描任務：用 node-cron 每日 09:00 掃描 mgm_finance_summary 最新月份，比對 alert_rule，觸發的寫入 alert_log。
  3. Email 發送：整合 nodemailer，發送 HTML 格式預警郵件（含指標值、閾值、建議處置連結）。
  4. LINE 推播：整合 LINE Messaging API（需申請 Channel Access Token），發送文字 + 圖片卡片。
  5. 簡訊備援：整合簡訊業者 API（如台灣大簡訊），作為 Email/LINE 未讀時的備援通知。
  6. 通知紀錄頁面：新增「預警紀錄」頁面，主管可查看歷史通知與確認已讀。

所需資源

npm 套件nodemailer、node-cron、axios（LINE/簡訊 API）
外部服務SMTP 郵件伺服器、LINE Business Account、簡訊業者帳號
資料庫新增 alert_rule + alert_log 表
環境變數SMTP_HOST、LINE_TOKEN、SMS_API_KEY

預期效果

主管不必每天登入系統，風險一出現即刻在手機收到通知。把「事後善後」變為「事前預防」，財務危機在萌芽階段就被處理。

關鍵技術
現金滾動預測算法

功能目標

結合應收到期日、應付到期日、貸款還本計畫，產出未來 13 週現金滾動預測，提前預警資金缺口，協助主管安排融資或催收。

具體實施步驟

  1. 現金流入預測：從 ermm_arap_detail 抓應收餘額與預計收款日，依帳齡與歷史回收率估算每週現金流入。
  2. 現金流出預測：從 mgm_invoice_details（AP）與 mgm_bank_loan_details（還本付息）抓預計付款日。
  3. 滾動預測算法：以當前現金餘額為起點，逐週加流入減流出，產出 13 週現金水位曲線；標示低於安全水位的週次。
  4. 後端 API：GET /api/cash/forecast?bu_no&weeks=13 回傳每週期初、流入、流出、期末、安全標記。
  5. 前端圖表：在現金日記頁面加「未來 13 週現金預測」折線圖，紅色標示資金缺口週。

所需資源

資料庫可能需新增 cash_forecast_log 記錄歷史預測準確度
財務顧問確認安全現金水位門檻與回收率假設

預期效果

主管提前 3 個月知道何時缺錢，主動安排融資或加速催收，避免臨時周轉危機。現金管理從被動變主動。

功能目標

預期效果

預算差異分析更準確，排除「產量變動」干擾，真正反映管理效率。

功能目標

導入自然語言問答，主管可用淺白語言提問（如「為什麼這個月毛利率下滑？」「哪個部門費用最高？」），系統自動解讀數據並給建議，降低財務門檻。

實施步驟重點

  1. LLM 接入：整合 OpenAI / Azure OpenAI / 本地 LLM API，建立 /api/ai/chat 介面。
  2. RAG 檢索：將 KPI 公式、財務指標定義、歷史數據摘要建立向量索引，提問時檢索相關上下文。
  3. 提示詞工程：設計財務分析專用 Prompt，約束 LLM 只基於系統數據回答，不得虛構。
  4. 前端對話介面：在儀表板加 AI 助理側邊欄，支援提問歷史與上下文記憶。

所需資源

外部服務LLM API（OpenAI gpt-4o-mini 或同等）、向量資料庫（Redis Vector 或 pgvector）
環境變數OPENAI_API_KEY、LLM_MODEL
安全敏感財務數據需脫敏後再送 LLM，建議用本地模型或 Azure 合規方案

預期效果

非財務背景的主管也能輕鬆讀懂財務數據，決策不再依賴財務部翻譯，大幅提升決策效率。
