## 二、补齐方案

### 2.1 设计原则

| 原则 | 做法 |
|------|------|
| 保留季节性 | 每月以 **2024 年同月**为模板，而非全年平均值 |
| 维持财务结构 | 金额列 ×0.9，比率列（毛利率/负债率/周转率）原样保留，`A = L + E` 自动成立 |
| 金额精确守恒 | 按「分」拆分，末条差额兜底，`Σ子项 = 母项` |
| 幂等 | 每月先清理本次生成的发票再重建，重复执行结果一致 |
| 可回滚 | 内置 `--rollback`，含孤儿行原值还原 |
| 影响面可控 | 只写 HN + 2023，其他账套/年份零改动 |

### 2.2 每月生成内容

```
mgm_finance_summary      1 行   （12 列金额 ×0.9，其余继承模板）
mgm_invoice_details AP   5 条   合计 = sale_cost_amt
mgm_invoice_details AR   5 条   合计 = sale_amt
```

### 2.3 金额拆分算法

```js
const WEIGHTS = [0.18, 0.22, 0.24, 0.16, 0.20];  // 合计 1.00

function allocate(totalCents, weights) {
    const parts = weights.map(w => Math.round(totalCents * w));
    const used = parts.slice(0, -1).reduce((a, b) => a + b, 0);
    parts[parts.length - 1] = totalCents - used;   // 差额兜底
    return parts;
}
```

- 先转「分」避免浮点误差
- 前 4 条四舍五入，第 5 条 = 总额 − 前 4 条 → **合计必然精确相等**

### 2.4 字段生成规则

| 字段 | 规则 | 示例 |
|------|------|------|
| 进项发票号 | `APHN{YYYY}{MM}00{1-5}` | `APHN202301001` |
| 销项发票号 | `ARHN{YYYY}{MM}00{1-5}` | `ARHN202301001` |
| 进项订单号 | `POHN{YYYY}{MM}00{n}` | `POHN202301001` |
| 销项订单号 | `SOHN{YYYY}{MM}00{n}` | `SOHN202301001` |

```js
// tax_rate 在库中以百分数字面量存储（13 表示 13%），必须再除以 100
const vat = Math.round(cents * 13 / 100) / 100;
```

## 六、残留风险与说明

| 优先级 | 事项 | 说明 |
|--------|------|------|
| **P0** | 数据性质 | 2023 年 HN 的财报与发票为**模板推导生成**，非真实历史账。用于演示与下钻完整性，不可作为对外报送依据 |
| P1 | 孤儿行已清理 | 原 3 条 `供应商X/Y/Z` 记录（197,579.00）已被 5 条规范进项替代；回滚可原值还原 |
| P1 | 季节性为继承值 | 2023 各月曲线形状源自 2024 同月数据 ×0.9，若 2023 实际季节分布不同，需以真实数据替换 |
| P2 | 2 月与 12 月金额相同 | 模板 2024-02 与 2024-12 本身相同，导致 2023 对应月份也相同（非生成缺陷） |
| P2 | 无审计留痕字段 | 未记录生成批次号，如需追溯建议增加 `data_source` 标记列 |
| P3 | 发票号无唯一索引 | `APHN202301001` 等命名规则理论上可能与其他批次撞号 |
