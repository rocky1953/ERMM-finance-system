---

## 一、问题现象

仪表板「销货成本」柱体支持下钻，点击后调用：

```
GET /api/invoice?bu_no=<账套>&YYYY_MM=<月份>&TX_type=AP
```

2023 年任意月份点击后，弹窗显示「尚无发票数据」。而 2024、2025 年同操作有数据。

---

## 二、根因定位

查询 `mgm_invoice_details` 中 `TX_type='AP'` 的覆盖情况，发现数据缺失并非全表为空，而是**逐月结构性缺失**：

| 账套 | 2023 年 AR（销项） | 2023 年 AP（进项） | 2024/2025 AP |
|------|------------------|------------------|-------------|
| HM | 1–12 月各 5 条 | **仅 2023-01 有 3 条占位数据** | 每月 7 条 |
| SZ | 1–12 月各 5 条 | **仅 2023-01 有 3 条占位数据** | 每月 7 条 |
| HN | 无 2023 年数据 | 无 | 每月 5 条 |

结论：
1. **2023-02 ~ 2023-12 无任何 AP 记录** → 弹窗必然落空；
2. 2023-01 虽有 3 条，但金额合计 ≠ 销售成本 → 即使能打开弹窗，下钻金额也对不上；
3. 2024/2025 虽每月有 7 条，但**金额与销售成本严重偏离**（逐月差额 200 万 ~ 560 万，0/12 月份吻合），属同源数据质量问题。

因此本次对齐需同时解决「**有数据**」与「**数据金额正确**」两件事。

---

## 三、修复方案

### 3.1 设计原则

| 原则 | 做法 |
|------|------|
| 以财报为唯一基准 | 每月拆分的进项发票合计必须**精确等于** `sale_cost_amt` |
| 不删除任何既有数据 | 已有行按 `uid` 升序**原地 UPDATE** 复用，不足才 INSERT |
| 分位精度不丢失 | 按「分」为单位拆分，最后一张用差额兜底 |
| 字段与既有数据同构 | 复用现有供应商名、`tax_rate=13`、`DB_CR='DR'`、`remark='进货发票'` |
| 可重复执行 | 幂等设计，重跑结果一致 |

### 3.2 金额拆分算法

```js
const WEIGHTS = [0.18, 0.22, 0.24, 0.16, 0.20];   // 合计 1.00

function allocate(totalCents, weights) {
    const parts = weights.map(w => Math.round(totalCents * w));
    const used = parts.slice(0, -1).reduce((a, b) => a + b, 0);
    parts[parts.length - 1] = totalCents - used;   // 差额兜底，保证合计精确
    return parts;
}
```

- 总金额先转「分」（`Math.round(x * 100)`），避免浮点误差；
- 前 4 张按权重四舍五入，第 5 张 = 总额 − 前 4 张，**合计必然精确相等**。

### 3.3 税额计算

```js
// tax_rate 在库中以百分数字面量存储（13 表示 13%），故需再除以 100
const vatAmt = Math.round(parts[i] * TAX_RATE / 100) / 100;
```

### 3.4 多余行处理

2024/2025 每月原有 7 行，本方案只生成 5 行。第 6、7 行若保留原金额，合计仍会偏移，故追加一步：

```sql
UPDATE mgm_invoice_details
   SET sub_amt=0, VAT_amt=0, payment=0, remark='数据校正-冗余行清零'
 WHERE uid=?
```

**不 DELETE**，保留行以便追溯；清零行在弹窗中显示为 0 金额，不影响合计。

### 3.5 生成字段

| 字段 | 生成规则 | 示例 |
|------|---------|------|
| `invoice_no` | `AP{bu}{YYYY}{MM}{序号3位}` | `APHM202306001` |
| `order_id` | `PO{bu}{YYYY}{MM}{序号3位}` | `POHM202306001` |
| `client_id` | 固定 5 家供应商循环 | 钢材供应商A / 塑胶原料B / 电子零组件C / 包装材料D / 能源供应E |
| `wk_date` | 当月 3 / 8 / 12 / 19 / 26 日 | `2023-06-03` |

## 六、过程中的缺陷与修复

修复过程中共发现并解决 4 个问题，均已回归验证。

| # | 问题 | 现象 | 根因 | 修复 |
|---|------|------|------|------|
| 1 | 税额放大 100 倍 | 首轮写入后税额 5,230 万（应为 52 万） | 本库 `tax_rate` 以百分数字面量存储（`13` = 13%），脚本少除一次 100 | `Math.round(parts[i] * 13 / 100) / 100` |
| 2 | 参数化后查不到数据 | `--year=2024` 返回 0 目标行 | SQL 写成 `YYYY_MM IN ('2024-%','2025-%')`，`IN` 不做模式匹配，把 `'2024-%'` 当字面量精确匹配 | 改为 `(YYYY_MM LIKE ? OR YYYY_MM LIKE ?)` |
| 3 | 校验差额达数百万 | 2024/2025 每月 diff 为 200 万 ~ 560 万 | 每月原有 7 行，脚本仅 UPDATE 前 5 行，第 6、7 行保留旧金额 | 追加多余行清零逻辑（`sub_amt=0`，不 DELETE） |
| 4 | 脚本年份硬编码 | 只能处理 2023 年 | 三处 `WHERE YYYY_MM LIKE '2023-%'` 写死 | 改为 `--year=YYYY` 可传参，支持多年份组合 |

> 问题 1 与历史上 VAT 算税「销项税放大 100 倍」属同一类陷阱，根因一致：`tax_rate` 是百分数字面量却被当成小数参与乘除。

## 七、残留风险与建议

| 优先级 | 风险 | 说明 | 建议 |
|--------|------|------|------|
| P1 | 数据为规则生成 | 进项发票按权重拆分生成，非真实采购单据 | 若用于真实账务，需以采购系统实际单据替换；当前仅为下钻展示的完整性补齐 |
| P2 | 清零行仍占位 | 96 行金额为 0，弹窗中会显示 0 金额行 | 若前端不希望展示，可在 `/api/invoice` 增加 `sub_amt > 0` 过滤，或前端过滤 |
| P2 | 2022 及以前年度未覆盖 | 本次仅处理 2023–2025 | 如需全量，`node scripts/seed_cost_invoices.js --year=2022 --apply` 即可 |
| P3 | 生成的发票号可能撞号 | `AP{bu}{YYYY}{MM}{序号}` 在高并发或人工导入时理论上可能重复 | 当前无唯一索引冲突；若后续建唯一索引需先清洗 |
